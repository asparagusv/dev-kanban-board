# Dev Kanban Board - 開発ジャーニーログ

**Dev Kanban Board** の開発ジャーニーへようこそ。このプロジェクトは、モダンな React 開発、厳格な TypeScript、そして開発者目線のデザインを追求したショーケースです。

## 🚀 ビジョン
このプロジェクトの目的は、以下の点に焦点を当てた、堅牢で高パフォーマンスな開発者向けカンバンボードを構築することでした：
- **パフォーマンス**: Vite と React 18 を活用し、高速な HMR を実現。
- **型安全 (Type Safety)**: 厳格な TypeScript 設定を使用し、コードの信頼性を担保。
- **UX**: 直感的なドラッグ＆ドロップ、永続的なステート、洗練されたダークモードの実装。

## 🛠 使用技術
- **フレームワーク**: [React 18](https://react.dev/)
- **ビルドツール**: [Vite](https://vitejs.dev/)
- **言語**: [TypeScript](https://www.typescriptlang.org/)
- **アイコン**: [Lucide-React](https://lucide.dev/)
- **アーキテクチャ**: カスタムフック、および `React.lazy` と `Suspense` によるコード分割。

### 💡 [MUI Typography] `variant` と `component` の華麗なる使い分け

MUI を使っていて、「ページのタイトルは `<h1>` タグにしたいけど、デフォルトの `h1` スタイルだと文字がデカすぎる...！」と悩んだことはありませんか？
CSS で無理やり上書きするのは、せっかくの MUI のテーマ管理を台無しにする **アンチパターン** です。

ここで登場するのが、`<Typography>` コンポーネントが持つ **「見た目と構造の分離」** という最強の設計思想です。

#### 実際のコード
```tsx
<Typography variant="h6" component="h1" sx={{ flexGrow: 1, fontWeight: 'bold' }}>
  Dev Kanban Board
</Typography>
```

#### 🛠 どう動いているのか？

- **`variant="h6"` (見た目の指定)**
  MUI のテーマで定義された `h6`（小さめの見出し）のスタイル（フォントサイズ、行間など）を適用します。
- **`component="h1"` (HTML 構造の指定)**
  見た目は `h6` のまま、HTML のDOMツリーとしては正しく `<h1>` としてレンダリングさせます。

### 🚨 [注意点: SEO とアクセシビリティの罠]

「文字を大きくしたいから `<h1>` を使う」「小さくしたいから `<h6>` を使う」という、**見た目目的での HTML タグ選び** は絶対に避けるべきです。

- スクリーンリーダーなどの支援技術は、見出しタグ（`h1`〜`h6`）の階層構造を読み取ってユーザーにページの構造を伝えます。
- Google などの検索エンジン（SEO）も、`<h1>` を「そのページで最も重要なテーマ」として解釈します。

もし見た目だけでタグを選ぶと、機械にとって「意味不明な構造のページ」になってしまいます！

### 🚀 [応用・メリット: 構造は正しく、見た目は自由に]

`component` prop を使うことで、このジレンマを完全に解決できます。

> **「HTML のセマンティクス（意味・構造）は絶対。見た目は MUI に任せる」。**

この設計思想を身につけることで、アクセシビリティスコアを爆上げしながら、デザイナーの要求する洗練された UI を矛盾なく両立させることができるのです！

### 💡 [UI/UXの鉄則] `trim()` で「透明なゴミタスク」を許さない

タスクを追加する時、もしユーザーが誤ってスペースキーだけを叩いてエンターを押してしまったらどうなるでしょう？
対策をしていないと、**「中身のない、スペースや改行だけの見えないタスク」** が無限に生成されてしまいます。

これを防ぐためのシンプルかつ最強のガードマンが、JavaScript 標準の `trim()` メソッドです。

#### 実際のコード
```tsx
onKeyDown={(e) => {
  // 🚨 newTaskTitle が "   "（スペースのみ）の場合...
  if (e.key === 'Enter' && newTaskTitle.trim()) {
    addTask(newTaskTitle);
    setNewTaskTitle('');
  }
}}
```

#### 🛠 どう動いているのか？

- **`trim()` の役割**: 文字列の前後にある空白（スペース、タブ、改行）をすべて綺麗に削ぎ落とします。
- **暗黙の型変換（Truthy / Falsy）の利用**:
  - もし入力が `"   "` (スペース3つ) だった場合、`.trim()` を通すと `""` (完全な空文字) になります。
  - JavaScript の `if` 文では、空文字 `""` は **`false`（Falsy）** として判定されます。
  - 結果として、`addTask` は実行されず、ゴミタスクの混入を完璧にブロックできます。

### 🚨 [注意点: `.length > 0` の落とし穴]

よくあるアンチパターンとして `if (newTaskTitle.length > 0)` という書き方があります。
これだと、スペースが1つでも入っていれば `length` が `1` になってしまい、ガードをすり抜けてしまいます。

### 🚀 [応用・メリット: データの一貫性を最前線で守る]

> **「不正なデータは、ステート（状態）に入る前に UI 側で弾き返す」。**

バックエンドのバリデーションやステート側のチェックに頼る前に、入力の最前線（コンポーネントのイベントハンドラ）でサクッと弾く。`trim()` を一つ挟むだけで、ユーザーの意図しない誤操作を防ぎ、カンバンボードを常にクリーンな状態に保つことができます！

### 💡 [MUI のお節介対策] `&:last-child` で余白を強制リセット

MUI の `CardContent` を使ってカード型の UI を作る際、自分で「上下左右の余白は `16px` にしよう！」と `sx={{ p: 2 }}` を指定しても、なぜか **カードの下側だけ余白が広くなってしまう** ことはありませんか？

これは、MUI が良かれと思って設定している「デフォルト仕様（お節介）」が原因です。これをねじ伏せるための魔法のコードがこれです👇

#### 実際のコード
```tsx
<CardContent sx={{ 
  p: 2,                     // 上下左右に一律 16px の余白をあける
  '&:last-child': { pb: 2 } // MUI が勝手につける「最後の余白」を 16px に強制上書き！
}}>
```

#### 🛠 `&:last-child` とは何か？

これは CSS の **「擬似クラス」** と呼ばれる強力なセレクタです。
- `&`: 自分自身の要素（ここでは `<CardContent>`）を指します。
- `:last-child`: その中にある **一番最後の子要素** が対象であることを示します。

つまり、「CardContent の一番最後にいる要素」に対してのみスタイルを適用するという意味になります。

#### 🚨 なぜ `{ pb: 2 }` (padding-bottom) の上書きが必要なの？

実は、MUI の `CardContent` には標準で以下のような CSS が組み込まれています。

> **「CardContent の最後の子要素には、自動的に `padding-bottom: 24px` をつける」**

MUI のデザイナーは「カードの最後には少し広めの余白があったほうが視覚的に綺麗だ」と考えてこの仕様にしました。
しかし、これのせいで自分で `p: 2`（16px）と指定しても、最後の子要素だけは MUI の仕様が優先されて **強制的に 24px に広げられてしまう** のです。

### 🚀 [応用・メリット: ピクセルパーフェクトの実現]

このお節介な挙動を理解した上で、意図的に `'&:last-child': { pb: 2 }`（最後の余白も 16px にする）を指定することで、MUI のデフォルトスタイルを上書き（強制リセット）しています。

> **「フレームワークの『お節介』を知り、それを制御する」。**

これにより、カード内の余白が上下左右すべて `16px` で統一され、デザイナーが意図した通りの美しく整った UI を実現できるのです！

### 💡 [パフォーマンスと安定性] `<link>` を捨てて `@fontsource` を選ぶ理由

Google Fonts などの Web フォントを使うとき、思考停止で `index.html` に `<link href="...">` を貼り付けていませんか？
MUI（Material UI）をはじめとするモダンなフロントエンド開発において、それはもはや**アンチパターン**になりつつあります。

当プロジェクトでは、フォントを `npm` パッケージとして読み込む **`@fontsource`** 方式を全面的に採用しています。

#### 実際のコード (`main.tsx`)
```tsx
import '@fontsource/inter/300.css';
import '@fontsource/inter/400.css';
import '@fontsource/inter/500.css';
import '@fontsource/inter/700.css';
// ...roboto も同様
```

#### 🚀 なぜこの方式が「最強」なのか？

1. **オフライン対応と爆速化（Self-hosting）**
   外部サーバー（Google のサーバー）へフォントを取りに行かず、アプリの静的ファイルとして一緒にビルド・配信されます。ネットワークが不安定な環境でもフォントが確実に表示され、サードパーティへのリクエストが減るため**プライバシー保護と読み込み速度の向上**に直結します。
   
2. **「ガクッ」と変わる現象（FOUT）の最小化**
   Web フォント読み込み特有の、ページを開いた瞬間に一瞬だけ別のフォントが表示されてガクッと切り替わる現象（Flash of Unstyled Text）を、ローカル配信によって最小限に抑えることができます。

3. **管理のしやすさと明示的な依存関係**
   「どのフォントの、どの太さ（Weight）を使っているか」が、`main.tsx` のインポート文を見るだけで一目瞭然になります。不要な太さを読み込んでパフォーマンスを落とすミスも防げます。

> **「フォントは外部リソースではなく、アプリの依存パッケージ（コードの一部）として扱う」。**

これが、高速で安定した、真のモダン Web アプリケーションを構築するための最適解です！
