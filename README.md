# Dev Kanban Board - 開発ジャーニーログ

**Dev Kanban Board** の開発ジャーニーへようこそ。このプロジェクトは、モダンな React 開発、厳格な TypeScript、そして開発者目線のデザインを追求したショーケースです。

## 🚀 ビジョン
このプロジェクトの目的は、以下の点に焦点を当てた、堅牢で高パフォーマンスな開発者向けカンバンボードを構築することでした：
- **パフォーマンス**: Vite と React 18 を活用し、高速な HMR を実現。
- **型安全 (Type Safety)**: 厳格な TypeScript 設定を使用し、コードの信頼性を担保。
- **UX**: 直感的なドラッグ＆ドロップ、永続的なステート、洗練されたダークモードの実装。

## 🛠 使用技術
- **フレームワーク**: [React 18](https://react.dev/)
- **ビルドツール**: [Vite](https://vitejs.dev/)
- **言語**: [TypeScript](https://www.typescriptlang.org/)
- **アイコン**: [Lucide-React](https://lucide.dev/)
- **アーキテクチャ**: カスタムフック、および `React.lazy` と `Suspense` によるコード分割。

### 💡 [Zustand] `persist` ミドルウェアによる「自動保存の魔法」

ダークモードの設定やユーザーの好みを管理する際、ただ状態（State）を持つだけでは、ブラウザをリロードした瞬間に初期値へ戻ってしまいます。
これに対処するため、状態管理ライブラリ **Zustand** の強力な武器である `persist` ミドルウェアを導入しました！

#### 実際のコード (`useThemeStore.ts`)
```tsx
export const useThemeStore = create<ThemeState>()(
    persist(
        (set) => ({
            darkMode: true,
            toggleDarkMode: () => set((state) => ({ darkMode: !state.darkMode })),
        }),
        {
            name: 'kanban-dark-mode', // LocalStorage のキー名
        }
    )
);
```

#### 🛠 ここが賢い！ `persist` の役割

Zustand の `persist` は、ストアの内容が変わるたびに、裏側で**自動的に LocalStorage へ状態を保存してくれる**機能です。

- 開発者が手動で面倒な `localStorage.setItem(...)` や `getItem(...)` を書く必要は一切ありません。
- `name: 'kanban-dark-mode'` というのは、ブラウザの LocalStorage にデータを保存・復元する際に目印となるキー名です。

### 🚀 [応用・メリット: 最高のユーザー体験（UX）の提供]

> **「ユーザーの選択を絶対に忘れない」。**

この魔法のコードを挟むだけで、ユーザーがページをリロードしようが、一度ブラウザを閉じて翌日アクセスしようが、「ダークモードにしておいた」という設定が確実に復元されます。
無駄なストレージ管理コードを排除しつつ、シームレスで永続的な UX を提供できるのが、Zustand `persist` の最大の強みです！

### 💡 [アクセシビリティ] `IconButton` に `aria-label` が絶対に必要な理由

MUI の `IconButton` を使ってダークモードの切り替えボタンなどを実装する際、`aria-label` を付け忘れていませんか？
これを省略するのは、UI の品質を下げる**サイレント・アンチパターン**です。

#### 実際のコード (`App.tsx`)
```tsx
<IconButton onClick={toggleDarkMode} color="inherit" aria-label="toggle dark mode">
  {darkMode ? <Brightness7Icon /> : <Brightness4Icon />}
</IconButton>
```

#### 🚨 なぜ `aria-label` が必須なのか？

**1. アイコンには「テキスト」がないから**
通常のボタン（例: `<button>保存</button>`）であれば、中にテキストがあるため、スクリーンリーダーはそれを読み上げてくれます。しかし、`IconButton` の中身は通常、画像（SVGアイコン）だけです。
- ❌ **aria-label なし**: スクリーンリーダーはただ「ボタン」としか読み上げません。視覚障害を持つユーザーは、何のボタンか分からず途方に暮れます。
- ✅ **aria-label あり**: 「ダークモードの切り替え、ボタン」と読み上げられ、役割が完全に明確になります。

**2. 画像の「意味」をプログラムに教えるため**
人間は「太陽」や「月」のアイコンを見れば「あ、これはモード切替だな」と直感的に理解できます。しかし、プログラム（ブラウザやスクリーンリーダー、検索エンジン）はアイコンの形から意味を理解できません。
`aria-label` は、その「見た目の意味」をテキストとして定義し、人間とプログラムを繋ぐ**翻訳機**の役割を果たします。

### 🚀 [応用・メリット: 誰一人取り残さない UI 設計]

> **「見た目がカッコいいだけでは、未完成である」。**

`aria-label` を1行足すだけで、アプリケーションは「目で見て使う人」だけでなく、「耳で聞いて使う人」にも優しい、真にプロフェッショナルなプロダクトへと進化します。

### 💡 [パフォーマンス最適化] `useMemo` で Theme の無駄な再生成を防ぐ

React アプリケーションにおいて、MUI の `createTheme` は比較的重い（大きなオブジェクトを生成する）処理です。
ここを無頓着に扱うと、アプリ全体のパフォーマンスを著しく低下させる原因になります。

#### 実際のコード (`App.tsx`)
```tsx
// 🛡️ darkMode が変わった時"だけ" テーマオブジェクトを再生成する
const theme = useMemo(() => createAppTheme(darkMode ? 'dark' : 'light'), [darkMode]);
```

#### 🚨 なぜ `useMemo` が必要なのか？（もし無かったら？）

もし `useMemo` を使わずに `const theme = createAppTheme(...)` と直接書いた場合、どうなるでしょうか？

React の関数コンポーネントは、再レンダリングされるたびに「関数の中身を上から下まで全て再実行」します。
つまり、入力フォームで **1文字タイピングするたび** に、巨大なテーマオブジェクトがゼロから作り直されてしまうのです。これは非常に非効率です。

`useMemo` でラップすることで、「`darkMode` が切り替わらない限り、前回の計算結果（キャッシュ）を使い回してね！」と React に命令でき、無駄な再計算を完璧に防ぐことができます。

### 🚀 [応用・メリット: 「一生変わらないテーマ」の正しい書き方]

もし、「ダークモード切り替えなんて無い。テーマは完全に静的だ」という場合、毎回生成させないための「2つの正解」があります。

**A. コンポーネントの外に出す（最も推奨）**
関数コンポーネントの外に定義された変数は、アプリ起動時に1回だけ評価されます。一番クリーンで最速です。
```tsx
// ✅ 定義はコンポーネントの外！一度しか実行されない
const staticTheme = createTheme({ ... });

function App() { ... }
```

**B. `useMemo` で依存配列を空にする**
何らかの理由でコンポーネント内の Props などを使いたい場合は、依存配列を空 `[]` にします。
```tsx
function App() {
  // ✅ 依存配列が空なので、初回レンダー時の1回しか実行されない
  const theme = useMemo(() => createTheme({ ... }), []);
  // ...
}
```

> **「React の再レンダリングの仕組みを知り、重い処理を適切にキャッシュする」。**

このパフォーマンスに対する執念こそが、サクサク動く「触り心地の良い」アプリケーションを生み出すのです！

### 💡 [HTMLの罠] ファイルアップロード後の `e.target.value = ''` の重要性

ファイルのインポート機能を実装する際、処理の最後に `e.target.value = '';` という一行を入れています。
これがないと、「同じファイルを2回連続で読み込めない」という非常に厄介なバグを引き起こします。

#### 実際のコード (`importTasks`)
```tsx
const importTasks = (e: React.ChangeEvent<HTMLInputElement>) => {
  // ... ファイル読み込み処理 ...
  reader.readAsText(file);
  
  // 🚨 最後に絶対に Input を空っぽにする！
  e.target.value = '';
};
```

#### 🛠 `onChange` イベントの罠

`<input type="file">` の `onChange` イベントは、文字通り **「選択されたファイル（値）が変化したとき」** にしか発火しません。

もし `e.target.value = '';` でリセットしなかった場合、以下の悲劇が起きます。
1. ユーザーが `data.json` を選択 → `onChange` 発火（成功！🎉）
2. 画面上のタスクをいくつか削除する。
3. 「あ、やっぱりさっきのデータをもう一度インポートし直そう」と思い、**再び同じ `data.json` を選択する。**
4. ブラウザ：「ん？さっきと同じファイルじゃん。値は変化してないね」 → **`onChange` が発火しない！（無反応）😱**

#### 🚀 [応用・メリット: 枯れた技術で堅牢な UI を作る]

今回、MUI の `Button` をラベルとして使い、その中に透明な `input` を仕込むというスマートな実装を行っています。

```tsx
<Button component="label">
  Import
  <input type="file" onChange={importTasks} hidden />
</Button>
```

この「ボタンを押すと背後の input が反応してファイル選択ダイアログが開く」という美しい HTML の仕組みを活かすには、ブラウザの唯一のフックである `onChange` を確実に発火させる必要があります。

> **「一回きりのアクションは、終わった瞬間にいつでも次を受け入れられる状態に戻す」。**

送信したからといって勝手にリセットされないのが HTML の基本です。この「枯れた（昔からある安定した）実装パターン」を知っているかどうかが、プロのフロントエンドエンジニアの分かれ道になります！

### 💡 [Zustand のキホン] `useState` との違い：なぜ `tasks:` が必要なのか？

React 標準の `useState` から Zustand へ移行したとき、ステートの更新方法（`set` 関数の書き方）に戸惑うかもしれません。
例えば、タスクを追加するときの書き方は以下のように異なります。

**React の `useState`:**
```tsx
setTasks((prev) => [...prev, newTask])
```

**Zustand の `set`:**
```tsx
set((state) => ({
    tasks: [...state.tasks, newTask]
}))
```

#### 🛠 なぜこのような書き方になるのか？

React の `useState` は、「そのステート（この場合 `tasks` 配列）専用の更新関数」です。だから単純に新しい配列を返せば済みました。

しかし Zustand の `set` 関数は、**「ストア全体の共通関数」** です。ストアの中には `tasks` だけではなく、`wipLimits` などの別の状態も同居しています。

1. **`...state.tasks` を展開する理由**:
   引数に入ってくる `state` はストア全体の親オブジェクトです。タスクの配列を取得するには、`state.tasks` のようにプロパティへアクセスする必要があります。
2. **`tasks: ...` と書く理由**:
   `set` 関数に「ストアの中の**どのステートを**これにするのか」を明示的に伝える必要があります。そのため、更新したいプロパティをキーとしたオブジェクト `{ tasks: ... }` を返す仕様になっています。

### 🚀 [応用・メリット: TypeScript による強力なガード]

もしうっかり `useState` の癖で、以下のように間違えてしまったらどうなるでしょうか？

```tsx
// ❌ 間違い: オブジェクトではなく配列を返してしまっている
set((state) => [...state.tasks, newTask]) 
```

ご安心ください。Zustand は TypeScript と極めて相性が良く、即座にエディタが真っ赤になって以下のようなエラー（イメージ）を出してあなたを守ってくれます。

> *「ストアはオブジェクト（`{ tasks: ... }`）を期待しているのに、配列が渡されました。これではどのステートを更新していいか分かりません！」*

Zustand は、状態管理を一元化するパワフルな機能を提供しながらも、型の力によって開発者の「うっかりミス」を許さない、非常に堅牢な設計になっています！

### 💡 [Zustand の深淵] `get` と `set` の真の役割と「カプセル化」

タスクのステータスを移動させる `moveTaskToStatus` などの複雑なアクションを見ると、`set` だけでなく **`get()`** という関数が登場します。
これらは Zustand の中核をなす機能ですが、実は非常に厳格なルールに基づいて使われています。

#### 実際のコード
```tsx
moveTaskToStatus: (taskId: number, nextStatus: TaskStatus) => {
    // 💡 get: Store内部で「今の値をちょっと貸して」と頼むための窓口
    const state = get();
    
    const currentTask = state.tasks.find((task) => task.id === taskId);
    if (!currentTask || currentTask.status === nextStatus) return;

    // 現在の state から上限(WIP Limit)をチェック
    const limit = state.wipLimits[nextStatus];
    if (limit !== undefined) {
        // ... チェックロジック ...
    }

    // 💡 set: Store内部で「この値に書き換えて」と命令するための窓口
    set((state) => ({
        tasks: state.tasks.map((task) => /* 更新処理 */)
    }));
}
```

#### 🛠 `get` と `set` とは何か？

- **`get`**: ストア内部のロジック（アクション）の中で、**現在の最新のステートを読み取る（参照する）** ための関数です。「更新する前に、今のタスクの数を確認したい」といったバリデーションや計算を行う際に必須になります。
- **`set`**: 先述の通り、ステートを**上書き更新する**ための関数です。

#### 🚨 [超重要] なぜ外のコンポーネントで直接呼ばないのか？

`set` も `get` も、Zustand の `create` 関数の引数として渡されるものであり、**Store の定義内（内部）でしか存在しません。**

これには明確な意図があります。もしコンポーネント（UI側）から自由に `set` を呼べてしまうと、「誰がどこでどんな風にステートを書き換えたか」が追えなくなり、バグの温床になります。

#### 🚀 [応用・メリット: 堅牢なラップ（カプセル化）]

そのため、直接的な更新手段は外に漏らさず、必ず以下のように **「具体的なアクション名でラップして」** 外の世界（コンポーネント）に公開します。

```tsx
// 外部には `setTasks` という分かりやすい名前の関数だけを見せる
setTasks: (tasks: Task[]) => {
    set({ tasks });
}
```

> **「UI 側には『何をするか（What）』だけを公開し、『どうやるか（How）』は Store 内に隠蔽せよ」。**

この「カプセル化」の原則を徹底することで、コンポーネントは見た目の描画に集中し、複雑なドメインロジック（WIP制限など）はすべて Store 内部（`get` と `set` の間）で安全に処理される美しいアーキテクチャが完成します！

### 💡 [JS の罠] アロー関数の `() => ({ ... })` にある丸カッコ `()` の正体

Zustand の設定や React のコンポーネントを書いていると、以下のような「丸カッコで波カッコを囲む」構文をよく目にします。

```tsx
// ✅ 正しい書き方（丸カッコあり）
persist(
    (set) => ({
        darkMode: true,
        toggleDarkMode: () => set((state) => ({ darkMode: !state.darkMode })),
    }),
    // ...
)
```

これを「丸カッコなんて要らないのでは？」と思って外してしまうと、**突然エラーが爆発**します。

```tsx
// ❌ エラーになる書き方（丸カッコなし）
persist(
    (set) => {
        darkMode: true, // 😱 エラー！
        toggleDarkMode: () => ...
    },
)
```

#### 🛠 なぜ `()` がないとエラーになるのか？

これは JavaScript のアロー関数（`=>`）の「2つの書き方」という仕様に原因があります。

**A. ブロック構文（中身が複数行になる場合）**
波カッコ `{}` で囲むと、JavaScript はそれを「処理を書くためのブロック」として解釈します。この場合、明示的に `return` を書かない限り、関数は何も返しません（`undefined` になります）。
```tsx
(set) => {
    // 💡 波カッコは「処理のブロック」と見なされる
    const newValue = true;
    return { darkMode: newValue }; // ⚠️ ここで return が絶対に必要！
}
```

**B. 簡略構文（1行で直接値を返す場合）**
波カッコ `{}` を使わなければ、`return` を省略して直後の値を返すことができます。

#### 🚨 罠の発動条件

では、**「オブジェクト（波カッコ `{}` で作られる値）」を「簡略構文」で返したい場合**はどうなるでしょうか？

```tsx
(set) => { darkMode: true }
```
こう書いてしまうと、JavaScript は最初の `{` を見た瞬間に、「おっ、これは**処理ブロックの開始だな！**」と勘違いしてしまいます。
そして `darkMode:` の部分を「オブジェクトのキー」ではなく、「ラベル（`goto` 文などで使われる古い構文）」として解釈し、その後のカンマ等で構文エラーを引き起こすのです。

#### 🚀 [解決策とメリット: 丸カッコによる「これは式だ！」という強制]

この勘違いを防ぐための魔法が、丸カッコ `()` です。

> **「丸カッコで囲まれたものは、絶対に『1つの値（式）』として解釈される」。**

```tsx
(set) => ({ darkMode: true })
```
こうすることで、「この `{}` は処理ブロックではなく、ただのオブジェクト（値）だよ！」と JavaScript エンジンに強制的に教えることができます。
結果として、`return` を書かずにスッキリと1行でオブジェクトを返すことができるのです！この仕様を知っておくと、不要なバグや TypeScript のエラーに悩まされることが劇的に減ります。
